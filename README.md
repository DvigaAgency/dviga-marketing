# dviga-marketing — копия главной dviga.marketing без рантайма Tilda

Статическая копия **главной страницы** сайта агентства DVIGA (https://dviga.marketing/): тот же дизайн, тексты, изображения, адаптив и анимации, но вместо Tilda-скриптов и Tilda-стилей — собственный CSS (один файл + инлайн-критический) и JS (~10 КБ min, ~4 КБ gzip, без зависимостей).

> Область работ: **главная страница** (шапка, футер, все её попапы и формы), **каталог кейсов** `/cases/` (с новой фильтрацией), **все 61 страница кейсов**, блог `/blog/` и две статьи, страницы услуг `/services/` и все 25 страниц, на которые ведут её карточки — см. раздел «Страницы кейсов и блога». Остальные страницы сайта (/about, остальные статьи блога, города «разработка сайта на Тильде в …», …) в копию не входят; ссылки на них ведут на оригинал `https://dviga.marketing/...`. Англоязычная версия `en.dviga.marketing` не копируется. Полный список страниц Tilda-проекта — [reports/tilda-pages.md](reports/tilda-pages.md) (238 страниц).

## Быстрый старт

```bash
npm install
npm run build        # dist/ — готовая статика (исходный HTML — снимок data/home.source.html; обновить: node tools/fetch-html.mjs)
npm run preview      # http://localhost:4173 (отдаёт dist/ со сжатием brotli/gzip)
npm run audit        # проверка: нет Tilda/запрещённых хостов, нет битых ссылок
```

Требования: Node ≥ 20. Для Playwright — `npx playwright install chromium`, для Lighthouse — установленный Google Chrome.

Переменные сборки: `SITE_URL` (по умолчанию `https://dviga.marketing`; canonical/og/sitemap/JSON-LD), `INDEX=1` (**по умолчанию сайт закрыт от индексации**: на каждой странице `<meta name="robots" content="noindex,nofollow">`, в `_headers` — `X-Robots-Tag`, в `robots.txt` нет sitemap, `sitemap.xml` не создаётся; `INDEX=1` — только для боевого запуска; `tools/audit-dist.mjs` проверяет noindex на всех страницах), `OUT` (каталог вывода), `CSS_MODE=link|async|inline` (доставка CSS; по умолчанию один блокирующий файл — см. ниже), `NO_CV=1` (отключить `content-visibility`).

### Раскладка Zero-блоков (ядро замены)
Tilda хранит для каждого элемента координаты на каждом брейкпоинте (`data-field-*-res-*`) и применяет их скриптом. Копия делает то же **на этапе сборки**:

* значения каскадируются между брейкпоинтами так же, как в `tilda-zero` (текущий → более широкие → базовый);
* оси `axisx/axisy`, контейнеры `grid`/`window`, `valign` артборда, `height_vh` переводятся в `left/top/translate/height` на CSS;
* масштаб между брейкпоинтами (`upscale=window`) — **только CSS**: `--s: tan(atan2(100cqw, <R>px))` + стандартное свойство `zoom`. Ширина берётся из `cqw` (ширина без полосы прокрутки; контейнер — `container-type:inline-size` у `<main>`/`<footer>`/попапов), поэтому JS на resize не нужен;
* `line-height` у текстов округляется до целых px (`round(1.2em, 1px)`), как это делает `t396__fixElementsLineHeights` в Tilda;
* CSS записей (типографика, цвета, hover) переписывается css-tree: селекторы Tilda → короткие классы, значения по умолчанию вынесены в `base.css`;
* секции вне экрана пропускаются браузером (`content-visibility:auto`) с точным `contain-intrinsic-block-size`, посчитанным из данных артборда — высота документа совпадает с оригиналом ещё до прокрутки;
* всё, что выступает за секции (артборды с `overflow:visible`), клипается на уровне `main`/`footer` — как у корневого контейнера Tilda (иначе на телефонах появляется горизонтальная прокрутка).

### Анимации
Полная таблица — [reports/animations.md](reports/animations.md). Кратко: появление (fadein) — CSS-transition + один `IntersectionObserver`; hover/blockintoview — `@keyframes`, сгенерированные при сборке, переключение классов в JS; scroll-шаги и «пин» (в т.ч. увеличение видео в хиро) — один rAF-обработчик, «fixed» реализован через `transform` (внутри контейнера `cqw` `position:fixed` ведёт себя иначе); счётчик «50+», слайдер, drag-лента, попапы — отдельный код. Поддержан `prefers-reduced-motion`. Тяжёлая инициализация откладывается до первого кадра (иначе принудительная раскладка попадает в TBT).

### Формы
Все 4 формы (две Zero-формы, «Рассчитайте стоимость» — многошаговая, виджет «Давайте подскажем») используют общий модуль `src/js/forms.js`: маска телефона `+7__________`, валидация (обязательные поля, email, телефон, согласие), состояния ошибки/успеха с теми же текстами, выбор файлов. Отправка:

```
POST /api/lead   (multipart/form-data)
  поля формы по их name (Name, Phone, Email, comment, Checkbox, File[] …)
  form  — идентификатор формы, page — URL страницы
```

Заявки отправляет `src/js/lead.js`: на адрес из `<meta name="lead-url">` (переменная сборки `LEAD_URL`, по умолчанию `/api/lead`), с UTM-метками и `yclid` посетителя; после успешной отправки в Метрику уходит просмотр `/tilda/<форма>/submitted/` — как у форм Tilda. На `localhost` без бэкенда форма считает отправку успешной (dev-заглушка), на других хостах показывает «Не удалось отправить заявку…». Загрузка файлов (в оригинале — виджет Uploadcare) в копии — обычный `<input type=file>`; файлы воркер передаёт в Битрикс24, если задана переменная `FILE_FIELD` (см. «Воркер заявок»), иначе в лид попадают только их имена.

## Счётчики и заявки в Битрикс24

Что подключено на оригинале (проект Tilda 8290193, проверено через Tilda MCP) и как это воспроизведено в копии:

| Что | Оригинал | Копия |
|---|---|---|
| Яндекс.Метрика | счётчик `36522530` (вебвизор, карта кликов, отслеживание ссылок, точный показатель отказов) | тот же счётчик и параметры, `tools/lib/tracking.mjs`, грузится через 2 с после загрузки страницы; `noscript`-пиксель |
| Google Analytics | не подключён | — |
| Коллтрекинг | calltracking.ru / i-media, проект `13560` (скрипт подмены номера + пиксель `webhooks.i-media.ru`) | тот же скрипт `cc.calltracking.ru/phone.a0e70.13560.async.js` и пиксель |
| Заявки: Битрикс24 | интеграция «dvigamarketing.bitrix24.ru» (плюс Tilda CRM, Telegram, 2 вебхука `tilda.rvspace.ru`) | `server/lead-worker.js` создаёт лид `crm.lead.add`; остальные получатели не переносились |

Переменные сборки: `YM_ID`, `CT_PROJECT`, `CT_SCRIPT` (значения оригинала по умолчанию; `0` отключает), `LEAD_URL`. `npm run audit` проверяет, что на каждой странице есть счётчик Метрики и скрипт коллтрекинга (или нет вовсе, если отключены).

**Важно:** пока копия открыта на GitHub Pages, её посетители попадают в боевой счётчик Метрики и в статистику коллтрекинга. Чтобы этого не было, задайте `YM_ID=0` и `CT_PROJECT=0` (переменные репозитория, см. ниже), либо ограничьте домены счётчика в настройках Метрики. Коллтрекинг подменяет номер только на доменах, добавленных в проект `13560` в кабинете calltracking.ru.

**Воркер заявок.** GitHub Pages статический, поэтому `/api/lead` обслуживает отдельный Cloudflare Worker [server/lead-worker.js](server/lead-worker.js) (без зависимостей):

1. Битрикс24 → Разработчикам → Другое → Входящий вебхук, право «CRM (crm)». Адрес вида `https://dvigamarketing.bitrix24.ru/rest/<id>/<токен>/` — секрет.
2. Создать воркер с кодом из `server/lead-worker.js`; переменные: `BITRIX_WEBHOOK_URL` (как секрет), `ALLOWED_ORIGINS` (например `https://dvigaagency.github.io`), необязательно `RESPONSIBLE_ID` и `FILE_FIELD`.
   Файлы из форм: в Битрикс24 → CRM → Лиды → Настройки → Настройка полей создать поле типа «Файл» (множественное), взять его код (`UF_CRM_…`) и записать в `FILE_FIELD`. Суммарно до 10 МБ на заявку; что не влезло, остаётся в комментарии лида только именем.
3. В репозитории (Settings → Secrets and variables → Actions → Variables) задать `LEAD_URL` — адрес воркера. После следующего пуша формы отправляют заявки в Битрикс24.

Воркер проверен на подставном Битрикс24 (поля лида, UTM, отказ чужому Origin и заявке без телефона/email); боевой вебхук в проекте не использовался.

## Страницы кейсов и блога

Сборка многостраничная (67 страниц, `dist` ≈ 270 МБ вместе с картинками и роликами): список страниц — [tools/pages.mjs](tools/pages.mjs), каждая страница строится из своего снимка HTML (`data/pages/`) тем же конвертером Zero-блоков, что и главная; шапка, футер, попапы, cookie и виджет общие. Ссылки на страницы копии остаются локальными (`/cases/`, `/blog/…`), на остальные — ведут на оригинал.

| адрес | что это |
|---|---|

| `/cases/<имя>/` (61 страница) | страницы кейсов: структура и порядок блоков как в оригинале; список подхватывается из `data/pages/cases__*.html` автоматически |
| `/blog/` | листинг блога с вкладками-категориями и «Загрузить еще» (поведение T395/T400 портировано без jQuery, `src/js/tabs.js`) |
| `/blog/kak-optimizirovat-smetu-proekta/`, `/blog/ren-tv-obnovili-svoy-logotip-i-pozitsionirovaniye/` | две статьи |
| `/services/` | общая страница услуг (`data/pages/services.html`): карточки всех услуг, ссылки ведут на локальные страницы |
| `/services/<имя>/` (25 страниц) | страницы услуг (`data/pages/services__*.html`) — все, на которые ведут карточки `/services/`: сайты, брендинг, продвижение, нишевые страницы. Список подхватывается из `data/pages/services__*.html` автоматически. `/services/sozdaniye-i-razrabotka-saytov/` — с квизом-калькулятором (T1040, `src/js/quiz.js`), FAQ-аккордеоном (T668, `src/js/accordion.js`) и отзывами; остальные страницы собраны теми же блоками |

**Фильтры кейсов.** Внутри группы условия объединяются по «ИЛИ», группы между собой — по «И»; поиск идёт по названию и отрасли; состояние хранится в адресе (`?service=sites&industry=realty&q=…`). Распределение по фильтрам — [tools/lib/cases.mjs](tools/lib/cases.mjs): вкладки оригинала → «Сайты», «Брендинг», «Продвижение», «Автоматизация» (услуги) и «Недвижимость», «Логистические компании», «Производство» (отрасли); метка отрасли на карточке (Ритейл, FMCG, Туризм, Услуги, Таможня, …) дополняет отрасли (FMCG и ритейл, Туризм, Услуги и сервисы…), а слова в названии («нейминг», «фирменный стиль», «реклам…») — услуги «Нейминг», «Фирменный стиль». Один кейс может попадать в несколько фильтров.

**Сравнение с оригиналом:** `sh tools/page-compare.sh <имя> </путь/страницы>` (preview на :4173) — тот же pixelmatch-контроль по секциям и 6 ширинам, отчёт `reports/compare-<имя>.md`. Расхождения остаются только там, где оригинал сам недетерминирован (ленивые картинки при снимке, cookie-плашка) или где намеренно изменён каталог кейсов.

Блоги/кейсы дополнительно: свёрнутые вкладками записи получают `display:none` сразу в разметке (без вспышки), их стили грузятся отдельным файлом в простое после загрузки страницы.

**Блоки страниц услуг.** Кроме перечисленных ниже конвертируются: глобальные блоки Tilda (`data-record-type=121` + `data-alias-record-type`) обрабатываются как тип, на который они ссылаются (Zero 396, отзывы 525 — масштаб как на главной, «Загрузить еще» 400 — в px оригинала без масштаба, не-ссылочные/ошибочные пропускаются); обложка T018 с фоновым слайдером T833 (ken burns, `src/js/hero.js`: шаг 5 с, первый переход через 3 с после загрузки; слайды из записи T833, привязанной через `data-coverslider-rec-ids`); галерея-плитка T155 (запись 169, стили — `data/block-css/<id>.css`, увеличение по клику не переносится, как и у остальных `data-zoomable`); попап с видео T331 заменён ссылкой на страницу ролика (Rutube/YouTube) — внешние iframe в копию не грузятся. Для квизов и аккордеонов каждой записи нужен свой `data/block-css/<id>.css` (`node tools/extract-block-css.mjs <адрес страницы> <id записи>…`). Анимированные элементы Zero с размером в % (например, `height:120%` у фонового фото с параллаксом): обёртка `.sw` занимает 100% элемента, а не наследует процент (иначе размер применялся дважды).

**Новые типы блоков на страницах кейсов.** Кроме Zero-блоков конвертируются: галереи Zero (слайдер картинок со scroll-snap и точками, `src/js/gallery.js`), HTML-вставки с `<video>` (ролики хоста оригинала перекодируются в H.264 720p, ленивая загрузка), лайтбокс-галереи T746 (попапы `#popup:…`), обложка T160, таблица T431, якоря T215 (`#about`…). Фон самой записи (`background-color` в стиле записи) переносится в `#r<id>`.

**Статьи по ТЗ (`/blog/plyusy-i-minusy-sayta-na-bitrix/`).** Текст статьи лежит в `data/articles/<slug>.html` (части `<!--part:N-->`: между ними остаются записи Tilda — CTA «Созвонимся на 30 минут», плашка автора с цитатой), мета-данные, H1, крошки, цитата и `pin` — в `data/articles/<slug>.json`. `node tools/article-snapshot.mjs <slug>` собирает снимок `data/pages/blog__<slug>.html` из снимка опубликованной страницы (`<slug>.source.html`: шапка, обложка, плашка автора, «Свежие статьи») и заменяет тело записями типа `article`; их сборка — [tools/lib/article.mjs](tools/lib/article.mjs) + [src/css/article.css](src/css/article.css) (колонка, кегли и интервалы как у текстовых блоков остальных статей, но высота определяется текстом; таблицы, оглавление, врезка «важно»). Вид — как у эталонной статьи (`/blog/kak-uznat-dvizhok-sayta`): колонка 760px, оглавление со строками-разделителями и красными номерами, таблицы шириной в колонку текста, вид T431 (серая шапка, сетка 1px, [src/css/article-table.css](src/css/article-table.css); ширины колонок — `data-w`), FAQ — серые плашки-аккордеон (`src/js/accordion.js`), плашки без скруглений. В JSON-LD обновляется `dateModified` и добавляется FAQPage. Блок «Свежие статьи» заполняется карточками из листинга блога (`fresh` в JSON статьи, [tools/lib/fresh-articles.mjs](tools/lib/fresh-articles.mjs)): обложка, категории и время — из карточки листинга, название и ссылка — из настроек. Иконка кнопки (самолётик «Подписаться», `--icon` / `--icon-hover` в CSS записи) выводится конвертером Zero как `.bi`. Если у статьи есть `pin`, [tools/lib/blog-pin.mjs](tools/lib/blog-pin.mjs) при сборке ставит её карточку первой в сетке `/blog/` (вкладки «Все статьи» и «Сайты»): карточки до прежнего места сдвигаются на одну позицию — узлы Zero-элементов переезжают между записями рядов вместе со своими CSS-правилами, координаты и высоты рядов пересчитываются (`NO_PIN=1` отключает).

**Подготовка данных новых страниц:** `node tools/fetch-html.mjs --pages` → `node tools/trim-html.mjs` (урезание снимка) → `npm run assets` (сбор адресов картинок и роликов, скачивание, AVIF/WebP, H.264; прогон можно прервать и продолжить) → `npm run build`. `node tools/prune-assets.mjs` удаляет из `public/` неиспользуемые варианты ширин.

## Развёртывание и кэширование
Статика из `dist/`. Файлы в `dist/assets/` имеют хеш в имени → отдавать с `Cache-Control: public, max-age=31536000, immutable`; HTML — `no-cache`. В `dist/_headers` лежит готовый конфиг (Cloudflare Pages / Netlify). Для nginx:

```nginx
location /assets/ { add_header Cache-Control "public, max-age=31536000, immutable"; }
location = /index.html { add_header Cache-Control "no-cache"; }
gzip on; gzip_types text/css application/javascript image/svg+xml;   # лучше brotli on;
```

Включите сжатие на хостинге: замеры скорости сделаны с brotli (`tools/serve.mjs` сжимает как продакшен), без сжатия CSS (~300 КБ) заметно тормозит на медленных сетях. CSS доставляется одним блокирующим файлом (`CSS_MODE=link`): режимы `async`/`inline` проверены, но асинхронная загрузка вызывает вспышку «несобранной» вёрстки, а инлайн увеличивает HTML — выигрыша по Lighthouse нет.

## Решения по спорным местам

* Исходник — HTML опубликованной страницы (содержит полные `data-*` Zero-блоков); Tilda MCP использован для head-кода/JSON-LD страницы (воспроизведён как есть, логотип — локальный), проверки project CSS и справки по формату блоков; MCP-сервер ничего не менял в проекте. Данные из HTML и из браузера сверены: при расхождении побеждает то, что видно на экране.
* Шрифт Inter — те же woff2 (variable wght, latin+cyrillic), что отдаёт Google Fonts оригиналу; self-host, урезаны до реально используемых символов (67 → 43 КБ), `font-display:swap`, preload обоих файлов, fallback `Inter Fallback` с `size-adjust`. Файл `Inter-VariableFont_o.woff` из проекта Tilda не используется: в нём нет кириллицы, оригинал рисует текст Google-вариантом (проверено через CDP `getPlatformFontsForNode`).
* Слайдер: геометрия оригинала — результат взаимодействия slick и скрипта масштабирования блока (`zoom = (W−120)/1200` при 1200–1679 px, `W/1200` от 1680). Масштаб воспроизведён тем же CSS; стартовая позиция ленты — «с нулевого слайда» (у оригинала она плавает из-за гонки скриптов).
* Один `<h1>`; порядок заголовков и тексты не менялись (в оригинале `h3` «Разработка сайтов на Тильде» стоит перед `h2` «Услуги» — оставлено как есть).
* Расхождения самого оригинала воспроизведены как есть: «754 проекта» (форма) и «более 350 …» (текст), «Tilda Experts», написание «Тильде/Tilda».
* Внутренние ссылки на отсутствующие в копии страницы переписаны на абсолютные URL оригинала — «битых» внутренних ссылок нет (`npm run audit`).
* Три картинки слова «Кейсы» в эталоне измерены с 20-пиксельными превью (ленивая подгрузка Tilda не успевала) — в копии они имеют реальные пропорции, поэтому их высота в замерах анимаций отличается на 14–19 px; визуально секции совпадают.
* Репозиторий приватный; `NOINDEX` по умолчанию выключен — перед публикацией на тестовом домене включите `NOINDEX=1`.

## Известные различия с оригиналом

**Страницы услуг (24 новые + `/services/`), `reports/compare-services-<имя>.md`.** Расхождения сверх 2% на секцию остаются только там, где оригинал недетерминирован или отличие не в вёрстке: плашка cookie в футере (как на остальных страницах); слайдеры, галереи, лента-«драг» и обложка-слайдер T833 (кадр анимации при съёмке разный, высоты и геометрия совпадают); квиз — оригинал при съёмке ещё не пересчитал фиксированную высоту (разница 12–107 px на 480/320, после прокрутки совпадает); микросмещения текста на 0,2–0,8 px при масштабе 1,2 (3–7%, расположение и размеры совпадают); «Error get alias» (не переносится).

* Слайдер отзывов и видео недетерминированы (автоплей) — в сравнении скриншотов слайдер проверяется по высоте (метка «динамич.» в `reports/compare.md`), видео скрыты на обеих сторонах.
* Сглаживание текста у Tilda зависит от слоёв композиции; для честного сравнения скриншоты снимаются с `--disable-lcd-text`.
* Hero-ролик недоступен (см. выше).

## Публикация на GitHub Pages

Workflow `.github/workflows/pages.yml` собирает сайт при каждом пуше в `main` (и вручную) и публикует `dist/` на
`https://dvigaagency.github.io/dviga-marketing/`. Сборка для подкаталога: `BASE=/dviga-marketing npm run build`
(переменная `BASE` добавляет префикс ко всем путям `/assets/…`). Сайт закрыт от индексации (`noindex`), а заявки уходят на `LEAD_URL` (без него `/api/lead` недоступен)
— до настройки воркера формы покажут сообщение об ошибке отправки. Для боевого домена собирайте без `BASE`.

**Блоки со стандартной вёрсткой Tilda (квиз, аккордеон).** Их CSS нельзя воспроизвести вручную без потерь, поэтому `node tools/extract-block-css.mjs <адрес страницы> <id записи>…` (только чтение оригинала) сохраняет в `data/block-css/<id>.css` правила, реально применяемые к записи: в порядке документа, ограниченные записью (`:where(#r<id>)` — специфичность не меняется). Разметку собирает `tools/lib/blocks.mjs`, размеры остаются в px оригинала без масштабирования (Tilda не масштабирует такие блоки, на всех ширинах метрики совпадают с оригиналом).

**Schema.org.** JSON-LD берётся из оригинала у каждой страницы (главная — `data/jsonld.json`; остальные — из снимка `data/pages/*.html`). Если в одном `<script>` оригинала подряд записано несколько объектов (невалидный JSON, так у части кейсов), сборка разбирает каждый объект и публикует отдельным `<script>`. Адреса в разметке переписываются на `SITE_URL`.
